# Trace replay benchmark

The benchmark scores pointing quality offline. It replays a set of motion
traces through the firmware's own pipeline code on the host, measures each
stroke against its ground truth, and compares the scores with a committed
baseline. Agents and people can use it to judge a change to a stage or a
setting in seconds, without a keyboard.

It complements the regression replay in [`trace-replay.md`](trace-replay.md).
Regression fixtures fail when any output changes; the benchmark never fails on
a score and says only whether each score got better or worse.

**The benchmark is not the final word on feel.** Its metrics measure things we
can define precisely, on traces that are, for now, synthetic. A change that
scores better still has to feel better: live playground runs and tuning on the
keyboard (#108, #115) stay the final check before a change ships.

## Run it

```sh
cmake -S host -B build/host -G Ninja
cmake --build build/host
node host/replay/bench.js --build-dir build/host
```

This scores every fixture under `host/bench/fixtures` against
`host/bench/baseline.json` and prints one table per set. Useful options:

| Option | Effect |
| --- | --- |
| `--profile <file>` | Apply a tuner profile export (`zmk-pointing-tools/tuning-profile` v1) on top of every cursor fixture's settings, matched by stage `stableId`. |
| `--sensor-spans` | Give the pipeline each frame's sensor sample span even where the firmware path has none today (what-if for #113). |
| `--json <file>` | Write the full report: per-set scores, per-fixture and per-stroke values, and the baseline comparison. |
| `--markdown <file>` | Write the tables as Markdown (CI appends this to the job summary). |
| `--write-baseline` | Replace `host/bench/baseline.json` with the current scores. |
| `--fixtures <dir>` | Score another directory of sets (one subdirectory per set). |
| `--baseline <file>` | Compare against a different baseline. |

To see what a setting does, score it as a profile, for example
`--profile host/bench/profiles/short-rise.json`; the `change` column then
reads against the committed baseline.

Change the baseline only in a commit that explains why the scores moved,
the same way regression snapshots are updated.

The CI `checks` job runs the benchmark after the host tests and appends the
table to the job summary. That step never fails the build.

## Fixture sets and the held-out convention

```text
host/bench/fixtures/tune/      traces to develop and tune against
host/bench/fixtures/holdout/   traces kept out of tuning, reported separately
host/bench/baseline.json       committed scores of both sets
host/bench/profiles/           tuner profiles: precision.json (used by a
                               fixture), and deliberately worse settings
                               for checking the metrics: short-rise.json
                               (speed-rise 1 ms), long-rise.json (120 ms),
                               no-acceleration.json (flat curve)
host/bench/generate.js         generator of the synthetic fixtures
```

- Develop against `tune/`. Don't read `holdout/` fixtures, and don't pick
  between changes by their held-out scores. Look at the held-out table once,
  as a check, when a change is ready.
- If a change improves the tuning set but not the held-out set, it probably
  fits the known traces rather than the motion they stand for.
- Split real recordings by session, not by stroke: all strokes of one
  recording go to the same set. Put about a quarter of the recordings of each
  activity in `holdout/`.
- Never move a fixture between sets to change a score.

## The current fixtures are synthetic

Until the trace capture tool (#115) exists, every benchmark fixture is
generated by `host/bench/generate.js`. Each one says so: `metadata.synthetic`
is `true` and `metadata.provenance` names the generator and its model.
Regenerate them with:

```sh
node host/bench/generate.js
```

The generator is deterministic. It models the cases #116 names:

| Set | Fixture | Models |
| --- | --- | --- |
| tune | `slow-aim-bridges` | Sparse single-count frames from slow steady strokes (4 to 15 mm/s) at 684 CPI, Bridges curve. |
| tune | `slow-aim-precision` | The #113 case: slow strokes (5 to 30 mm/s) on the steep slow end of the Precision curve, applied from `profiles/precision.json`. |
| tune | `tremor` | Rest tremor (8.5 to 10.5 Hz) that the user doesn't mean, and slow strokes with tremor on top. |
| tune | `flicks-usb` | Minimum-jerk flicks peaking at 250 to 600 mm/s, with USB report pacing. |
| tune | `post-typing-cursor` | Ball shake from key presses, then an intended stroke 80 ms after the last key. |
| tune | `scroll-slow` | Slow, nearly straight left-ball scroll strokes at its effective 114 CPI. |
| tune | `scroll-curved` | Vertical scroll strokes that curve sideways by 23 to 46 degrees. |
| tune | `text-strokes` | Text navigation strokes with up to 14 degrees of drift. |
| holdout | `slow-aim-2052cpi` | Slow steady strokes at 2052 CPI, Bridges curve. |
| holdout | `flicks-ble` | The same kind of flicks, with Bluetooth report pacing. |
| holdout | `scroll-post-typing` | Left-ball shake from typing, then a scroll stroke 20 to 80 ms after the last key, inside the keypress guard. |

The sensor model behind all of them: the true ball position is sampled by the
sensor every 333 µs; a motion interrupt starts a read 200 to 600 µs after the
first new count; reads are at least 1 ms apart and return all counts since the
previous read; a frame reaches the pipeline 100 µs after its read. Counts come
from the quantized position, so no distance is lost in sampling.

Synthetic traces only check the cases someone thought to model. Real
recordings replace them as they arrive (see "Adding real recordings").

## Fixture format v2

Version 2 of `zmk-pointing-tools/trace-fixture` adds microsecond timing, the
sensor sample span, the source, the full cursor pipeline, and ground truth.
Version 1 fixtures keep working unchanged.

```jsonc
{
  "schema": "zmk-pointing-tools/trace-fixture",
  "version": 2,
  "id": "slow-aim-precision",
  "description": "…",
  "metadata": { "mode": "cursor", "synthetic": true, "provenance": "…" },
  "source": {
    "device": "right-ball",     // stable id of the pointing device
    "location": "central",      // central or peripheral half
    "cpi": 684,                 // resolution the frames are labelled with
    "span": "none"              // "sensor" if firmware gets the sample span
  },
  "processor": { "kind": "cursor-pipeline", "link": "usb", "stages": [ … ] },
  "events": [
    ["motion", 1350, 1, 0, 1350],  // delta µs, x counts, y counts, span µs
    ["keypress", 52000]            // delta µs
  ],
  "truth": { "strokes": [ … ] }
}
```

**Events.** The second field is the time since the previous event in
microseconds, measured when the frame reaches the pipeline. Replay hands each
stage the whole-millisecond arrival time firmware uses today (`floor(t / 1000)`),
so the coarse timing #113 is about shows up in replay. The optional fifth
field is the sensor sample span in microseconds: the time between the read
that produced the frame and the previous read. It reaches the pipeline only
when `source.span` is `"sensor"` (or with `--sensor-spans`).

**Processor.** Scroll, text, and noise fixtures keep their version 1
`settings`, except that the resolution comes from `source.cpi`. The cursor
pipeline lists its stages in pipeline order, as in a keymap:

```jsonc
"stages": [
  { "type": "orientation", "stableId": "right-cursor-orientation",
    "settings": { "invert-x": 1, "invert-y": 1 } },
  { "type": "normalize", "stableId": "right-cursor-normalize" },
  { "type": "gate", "stableId": "right-cursor-gate",
    "settings": { "enabled": 0, "activation-distance": 223, "coherence": 60,
                  "qualification-timeout": 160, "idle-timeout": 120 } },
  { "type": "acceleration", "stableId": "right-cursor-acceleration", "settings": { … } },
  { "type": "transfer", "stableId": "right-cursor-transfer", "settings": { … } },
  { "type": "quantizer", "stableId": "right-cursor-quantizer" },
  { "type": "coalescer", "stableId": "right-cursor-coalescer",
    "settings": { "usb-report-interval": 1, "ble-report-interval": 8 } }
]
```

Stage types are `orientation`, `normalize`, `gate`, `acceleration`,
`transfer`, `quantizer`, and `coalescer`. Settings use the tuning parameter
keys the firmware publishes and the tuner exports, in devicetree units, and a
tunable stage must set every parameter. The runner applies them through the
firmware's stage tuning code, so a value replays exactly as the device would
apply it. Orientation takes `swap-xy`, `invert-x`, and `invert-y`; the gate
also takes `suppress-after-keypress-ms`, the keypress guard its devicetree
node references. `link` selects the coalescer's USB or Bluetooth interval.

`processor.profile` may hold a tuner profile export
(`zmk-pointing-tools/tuning-profile` v1, from `web/profile.js`). Its values
override the inline settings of the stage with the same `stableId`; targets
for other stages are ignored. `--profile` applies a second profile on top.
A profile may hold only some parameters of a stage, as the tuner's import
allows; the rest keep the fixture's values.

**Ground truth.** `truth.strokes` lists the strokes of the trace. Each has an
`id`, an `activity` (`slow-aim`, `aim`, `tremor`, `flick`, `scroll`, `text`,
or `post-typing`), `intended` (whether the user meant the motion), and a
`startUs`/`endUs` window in fixture time. Optional fields feed the metrics:

- `speedMmPerS`: the true ball speed of a steady stroke. For a recording,
  the stroke's length over its duration.
- `axis`: the intended axis of a scroll or text stroke.
- `intendedOutput`: `[x, y]` the output the user wanted, in pointer units
  (cursor) or steps (scroll, text). For a recording, for example a playground
  target's displacement. Generated fixtures use the output an ideal pipeline
  with the fixture's own curve would give knowing the true speed, so under a
  `--profile` with another curve this measures against the fixture's curve.

## Metrics

Each metric is defined here before code computes it, so its meaning is fixed
before anyone optimizes against it. Change a definition only together with
the baseline, in a commit that says why.

Common rules:

- A stroke's **input frames** are the motion events with
  `startUs ≤ t < endUs`.
- A stroke's **output** is every report with
  `startUs ≤ t < min(endUs + 100 ms, next stroke's startUs)`. The 100 ms tail
  catches output the pipeline delays. Scroll and text reports carry only the
  whole millisecond they were sent at, so `startUs` is rounded down to a
  millisecond for this comparison.
- Ball distance is counts × 25.4 / CPI millimetres. Cursor output is in
  pointer units, scroll and text output in steps.
- A metric applies only to strokes that have the fields it needs; others are
  skipped. A set's score is the mean of the stroke values over every stroke it
  applies to, and the report shows how many strokes that was.
- Lower is better for every metric except axis-lock accuracy.

### Speed-estimate error (`speedErrorPercent`)

How far the cursor acceleration stage's speed estimate is from the stroke's
true speed. Applies to cursor strokes with `speedMmPerS` in a pipeline with an
acceleration stage. For each input frame at least 100 ms after `startUs` that
reaches the acceleration stage, the relative error is
`e = (estimate − speedMmPerS) / speedMmPerS`. The stroke value is the root mean
square of `e`, in percent. It counts both bias and frame-to-frame swing.

### Slow-stroke jitter (`slowJitterPercent`)

High-frequency energy in the cursor output path of a slow stroke. Applies to
intended cursor strokes with `speedMmPerS ≤ 50`. Output from 100 ms after
`startUs` to `endUs` is summed in consecutive 16 ms bins and projected on the
stroke's net output direction, giving `v₁ … vₙ`. Each bin is compared with the
mean of the bins up to three either side, `sᵢ`. The stroke value is
`RMS(vᵢ − sᵢ) / mean(v)` in percent. Sparse counts set a floor that every
pipeline shares and that dominates the value at the slowest speeds; output
smoothing lowers it, and tremor passing through raises it.

### Sensitivity stepping (`sensitivityStepPercent`)

How much the sensitivity the acceleration stage applies jumps from frame to
frame on a slow stroke: the "jagged steps between slow and normal speed" of
#113. Applies to the same strokes as slow-stroke jitter, in a pipeline with an
acceleration stage. Take the sensitivity applied to each input frame at least
100 ms after `startUs` that reaches the stage, `g₁ … gₙ`, as the stage
computes it from its speed estimate. The stroke value is
`RMS(gᵢ − gᵢ₋₁) / mean(g)` in percent. It is zero on a flat part of the curve
whatever the estimate does, so it scores how the estimate and the curve's
slope combine. Slow-stroke jitter, by contrast, mostly reflects how sparse the
counts are.

### Flick lag (`flickLagMs`)

How far output trails input during a flick. Applies to `flick` strokes. Input
progress is the cumulative input projected on the net input direction;
output progress the cumulative output projected on the net output direction,
each as a fraction of its total. For p = 10 %, 50 %, and 90 %, the lag is the
time of the first report reaching p minus the time of the first input frame
reaching p. The stroke value is the mean of the three lags in milliseconds.
Because progress is a fraction of each total, acceleration that ramps up
during a flick also adds lag; a flat curve has the least.

### Distance error (`distanceErrorPercent`)

Distance lost or gained over an intended stroke. Applies to intended strokes
with `intendedOutput`. Cursor output is the magnitude of the summed output
vector; scroll and text output is the net output along the intended axis
(text: right minus left, or down minus up). The stroke value is
`|actual − intended| / intended` in percent, comparing magnitudes, with
`intended` the magnitude of `intendedOutput`. Direction is not scored. The
JSON report also carries the signed value (`distanceBiasPercent`, negative
when distance is lost).

### Unintended output (`unintendedOutput`)

Output from motion the user didn't mean, such as tremor at rest or shake from
typing. Applies to strokes with `intended: false`. The stroke value is the
summed magnitude of every report: the Euclidean length of each cursor report,
or the absolute steps of each scroll or text report.

### Axis-lock accuracy (`axisLockPercent`)

Applies to scroll and text strokes with an `axis`. Of the stroke's input
frames on which axis intent has decided (anything but undecided), the share
whose intent is the intended axis, in percent. Higher is better.

### Sideways leak (`sidewaysLeakPercent`)

Applies to scroll and text strokes with an `axis`. The share of output steps
(absolute) that went to the other axis, in percent.

### Mid-stroke switches (`axisSwitches`)

Applies to scroll and text strokes with an `axis`. The number of times the
decided intent changes between consecutive decided input frames of the stroke.

## Adding real recordings

A recording becomes a fixture when it has:

1. `schema`, `version: 2`, an `id`, and a `description` of what was done.
2. `metadata.synthetic: false` and a `metadata.provenance` naming the
   keyboard, firmware commit, date, and the tool that captured it.
3. `source` with the device's stable id, its half, its CPI, and whether its
   firmware path carries a sample span.
4. The pipeline the device ran, as `processor.stages` and, ideally, the
   tuner's profile export in `processor.profile`.
5. Raw motion events with microsecond arrival times and sensor spans, and
   keypress events if they were recorded.
6. `truth.strokes` labelled by activity, with whatever ground truth is
   known: the steady speed, the intended axis, the playground target.

Put it in `tune/` or `holdout/` by the convention above, run the benchmark,
and commit the new baseline with it. Keep both synthetic and real fixtures
until the real set covers every case; then retire the synthetic ones in one
commit that also moves the baseline.
